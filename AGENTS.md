# Правила работы Analytics MVP

## Перед изменениями

1. Прочитайте ближайший `AGENTS.md`.
2. Проверьте `git status` и не затрагивайте неизвестные изменения.
3. Откройте только документы из маршрута задачи:
   - текущее состояние и ограничения — `PROJECT_STATE.md`;
   - активные задачи — `docs/ROADMAP.md`;
   - границы релизов — `docs/VERSIONS.md` и документ активной версии;
   - дизайн — `docs/DESIGN_SYSTEM.md`, `docs/UI_COMPONENTS.md`;
   - импорт — `docs/IMPORTS.md`;
   - товары — `docs/PRODUCT_REGISTRY.md`, `docs/PRODUCT_IMAGES.md`;
   - клиентский опыт — `docs/CLIENT_EXPERIENCE.md`;
   - отдельные модули — соответствующий документ в `docs/`.

## Границы изменений

- Не меняйте бизнес-формулы, схему данных, импорт или источник владения полями вне явной задачи.
- Исправляйте причину, а не визуальное следствие. После неудачной гипотезы повторно соберите диагностику.
- Для больших наборов используйте серверные агрегаты, пагинацию и диапазонные запросы; не загружайте весь датасет во frontend.
- Сохраняйте local-first архитектуру основных отчётов. Supabase используется только там, где это явно зафиксировано.
- Не добавляйте секреты, реальные пароли и `.env.local` в репозиторий.
- Не переписывайте страницу целиком, если задачу решает общий компонент или локальная правка.

## UI и дизайн

- Перед изменением интерфейса используйте навык `analytics-product-design`.
- `docs/DESIGN_SYSTEM.md` — единственный канонический источник визуальных правил.
- `docs/UI_COMPONENTS.md` фиксирует контракты переиспользуемых контролов.
- Если меняется общий паттерн, обновите оба документа и исходник навыка в `skills/analytics-product-design/`.
- Референсы адаптируются структурно; бренд, точные цвета и уникальные элементы не копируются.

## Проверки и публикация

- Минимум: `npm run build`.
- Для затронутого TypeScript/React-кода: `npm run lint`.
- Для клиентского опыта: `npm run test:cx`.
- После завершённого изменения обновите активный version-документ и roadmap, если изменился статус или архитектура.
- Принятые изменения коммитятся, отправляются в `main` и публикуются через GitHub Pages.

## Субагенты

- Постоянных проектных субагентов и файлов `.agents/` сейчас нет.
- Подключайте субагентов только для независимых параллельных исследований. Один агент не должен одновременно менять общие файлы с другим.
- Итоговая интеграция, проверки, документация и деплой остаются ответственностью основного агента.

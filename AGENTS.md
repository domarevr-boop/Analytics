# Правила работы Analytics MVP

## Перед изменениями

1. Прочитайте ближайший `AGENTS.md`.
2. Проверьте `git status` и не затрагивайте неизвестные изменения.
3. Откройте только документы из маршрута задачи:
   - карта актуальной документации — `docs/INDEX.md`;
   - текущее состояние и ограничения — `PROJECT_STATE.md`;
   - активные задачи — `docs/ROADMAP.md`;
   - границы релизов — `docs/VERSIONS.md` и документ активной версии;
   - дизайн — `docs/DESIGN_SYSTEM.md`, `docs/UI_COMPONENTS.md`;
   - импорт — `docs/IMPORTS.md`;
   - товары — `docs/PRODUCT_REGISTRY.md`, `docs/PRODUCT_IMAGES.md`;
   - клиентский опыт — `docs/CLIENT_EXPERIENCE.md`;
   - конкуренты — `docs/COMPETITORS.md`;
   - отдельные модули — соответствующий документ в `docs/`.

## Границы изменений

- Не меняйте бизнес-формулы, схему данных, импорт или источник владения полями вне явной задачи.
- Исправляйте причину, а не визуальное следствие. После неудачной гипотезы повторно соберите диагностику.
- Для больших наборов используйте серверные агрегаты, пагинацию и диапазонные запросы; не загружайте весь датасет во frontend.
- Сохраняйте local-first архитектуру основных отчётов. Supabase используется только там, где это явно зафиксировано.
- Не добавляйте секреты, реальные пароли и `.env.local` в репозиторий.
- Не переписывайте страницу целиком, если задачу решает общий компонент или локальная правка.

## UI и дизайн

- Перед изменением интерфейса используйте навык `analytics-product-design`.
- `docs/DESIGN_SYSTEM.md` — единственный канонический источник визуальных правил.
- `docs/UI_COMPONENTS.md` фиксирует контракты переиспользуемых контролов.
- Если меняется общий паттерн, обновите оба документа и исходник навыка в `skills/analytics-product-design/`.
- Референсы адаптируются структурно; бренд, точные цвета и уникальные элементы не копируются.

## Проверки и публикация

- Минимум: `npm run build`.
- Для затронутого TypeScript/React-кода сначала запускайте ESLint только по изменённым файлам. Полный `npm run lint` запускайте отдельно, если нужен аудит общего baseline; известные старые ошибки не должны блокировать сфокусированную задачу.
- Для клиентского опыта: `npm run test:cx`.
- После завершённого изменения обновите активный version-документ и roadmap, если изменился статус или архитектура.
- Принятые изменения коммитятся, отправляются в `main` и публикуются через GitHub Pages.

## Экономный режим работы

- Читайте крупные файлы точечно: сначала `rg`, затем только нужные диапазоны строк. Не выводите в контекст целые страницы, большие логи или документацию инструмента без необходимости.
- Сначала формулируйте минимальную проверяемую гипотезу и реализуйте основной путь. Дополнительные режимы подключайте после проверки базового контракта.
- Разделяйте независимые причины и изменения: аварийный production-fix, функциональная доработка и визуальная полировка выполняются отдельными этапами и коммитами.
- Браузерную проверку запускайте только когда в доступной сессии есть нужные данные или подготовлено репрезентативное тестовое состояние. Пустая сессия не оправдывает длительный визуальный аудит data-driven блока.
- Переиспользуйте один источник кодов, алиасов и констант; не создавайте временные дубли в компоненте.
- Перед публикацией используйте уже проверенный для этого worktree способ деплоя. Если стандартный `gh-pages` не видит remote, сразу передавайте `-r $(git config --get remote.origin.url)` в совместимом shell.
- В отчёте пользователю показывайте только итог проверок и релевантные ограничения; большие диагностические логи сохраняйте вне ответа.

## Субагенты

- Постоянных проектных субагентов и файлов `.agents/` сейчас нет.
- Подключайте субагентов только для независимых параллельных исследований. Один агент не должен одновременно менять общие файлы с другим.
- Итоговая интеграция, проверки, документация и деплой остаются ответственностью основного агента.

## Тестовый процесс Sol → Luna

1. Пользователь передаёт новую задачу агенту на GPT‑5.6 Sol.
2. Sol проводит необходимый read-only аудит и готовит план реализации для GPT‑5.6 Luna с reasoning `xhigh`; код на этом этапе не меняется.
3. План обязательно фиксирует доказанную причину или исходное состояние, контекст для чтения, точные файлы и границы изменений, порядок реализации, проверки, условия остановки и публикацию.
4. Пользователь переключает модель на GPT‑5.6 Luna с reasoning `xhigh` и отдельно разрешает выполнение.
5. Luna повторно проверяет Git-состояние и выполняет план. Если фактическое состояние расходится с планом или требуется расширение границ, реализация останавливается и возвращается к Sol для пересмотра.

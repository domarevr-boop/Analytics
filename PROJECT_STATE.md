## Архитектура

- Клиент: React 19 + TypeScript + Vite.
- Основные отчёты, планы, справочник и вычисляемые витрины работают local-first в браузере; «Отчётность» объединяет собственные локальные данные с агрегированным локальным отчётом «Рынок».
- В worktree V5 страница «Рынок» имеет отдельное opt-in чтение `v5_market_date_bounds` + `v5_market_series`. Оно разрешено только при `VITE_APP_ENV=v5-development` и `VITE_V5_MARKET_BACKEND_ENABLED=true`; при серверной ошибке локальные строки не подмешиваются. Остальные потребители отчёта пока остаются на локальном V4-store.
- Отзывы покупателей — отдельный серверный контур Supabase: импорт, дедупликация, таксономия, тональность, CXI, агрегаты и пагинация.
- Исходные файлы отзывов не хранятся постоянно: после пакетной записи и сверки числа строк временный объект удаляется.
- GitHub Pages публикует статический frontend. Секреты Supabase не должны попадать в клиентскую сборку; доступ регулируется RLS и RPC.

## Подтверждённый аудит для V5

- IndexedDB V4 использует схему 11 и 24 хранилища; импорт распознаёт 12 типов источников. Основная загрузка, валидация, сопоставление и merge выполняются в браузере.
- `CloudRepository` покрывает только часть сущностей и возвращает пустые наборы для истории склеек, географии, точек входа, поиска, рынка и конкурентов; большие наборы всё ещё загружаются во frontend. Это не готовая основа V5.
- CX подтверждает пригодность отдельных паттернов — Auth/RLS, private Storage, партии, дедупликация, версии методологии, RPC и пагинация. Его импорт при этом парсит и нормализует файл на клиенте, пишет несколькими запросами и удаляет исходник после проверки, поэтому целиком как универсальный backend не переносится.
- Серверных расписаний/фоновых заданий и доказанного восстановления Supabase пока нет. Recovery-процедура и безопасная проверка prerequisites подготовлены; read-only доступ CLI к пустому private Storage V5 подтверждён, но дамп БД блокирует отсутствие Docker/PostgreSQL tools, а Auth mapping требует отдельной проверки. Frontend V5 читает серверную роль: viewer допускается только к RPC-странице «Рынок», importer — также к ограниченному импорту «Рынка», admin — к полному переходному интерфейсу. Реальные отдельные аккаунты ещё не проверены.
- Историческая цепочка `supabase/migrations/` относится к V4/CX и не подтверждена как чистый bootstrap V5. Из ветки V5 удалены унаследованные CLI-link metadata и дублирующий устаревший `supabase/migration.sql`.
- Историческая цепочка V4/CX сохранена в `supabase/legacy-v4/` и исключена из активного `db push`. Активная цепочка V5 содержит foundation, управление доступом и первый источник `market_dynamics`: версионные дневные факты, сырые строки, серверную валидацию, атомарную публикацию, детерминированную замену версии, откат и агрегаты день/неделя/месяц. Project ref заблокирован защитным скриптом.

## Реализованные рабочие разделы

- Главная: месячные KPI, иерархическая таблица, планы, финансовые показатели, рекламные и воронковые метрики, связанные графики.
- Импорт: распознавание источников, точечная замена метрик, кабинетно-безопасное обновление, покрытие данных.
- Планирование: отдельные сворачиваемые годовые таблицы кабинетов с категориями, точные месячные планы и независимая сценарная модель Plan/Scenario/Δ. Утверждённый план редактирует сумму заказов, процент выкупа, процент к перечислению и рентабельность; сценарий — пять независимых драйверов. Применение сценария создаёт локальную резервную копию для однократного отката. Бренды и товары без категории исключены.
- Аналитика: воронка, точки входа, география заказов, поисковые запросы WB, рынок, конкуренты и «Отчётность». «Рынок» хранит ежедневные суммы и количество заказов, доли и средние чеки; его средний чек используется для денежной оценки поискового спроса. «Отчётность» сравнивает равные периоды, показывает собственные KPI и рынок, а также детализацию собственных показателей по кабинетам. Страница конкурентов использует локальный атомарный импорт четырёх листов Excel, сравнивает срез с нашим ассортиментом, анализирует многосерийную динамику и складские снимки, отдельно отслеживает структуру TOP‑10/20/50.
- Карточка товара: общие KPI, динамика, воронка, источники трафика и география.
- Клиентский опыт: обзор, отзывы, темы, методология и настройки анализа.

## Клиентский опыт

- Темы определяются опубликованным версионируемым словарём: `exact_keyword`, `lemma`, `lemma_phrase`, `context`.
- Тональность определяется отдельно от поиска темы и хранится на уровне совпадения.
- Тональность темы: `Positive / (Positive + Negative) × 100`; при отсутствии оценочных упоминаний возвращается `null`.
- CXI рассчитывается по оценочным упоминаниям и разделён на Overall, Product, Service и Outcome.
- Доступны полный перерасчёт при изменении логики и диапазонный перерасчёт для новых дат.
- Начальный период страницы — последний месяц, в котором есть данные.

## Активные ограничения

- Большая часть данных зависит от IndexedDB конкретного браузера и не синхронизируется между устройствами.
- Версия локальной IndexedDB изменяется только монотонно; текущая схема — 11. В ней хранятся история склеек, совокупные планы и глобальная настройка источника плана.
- Глобальный переключатель источника плана действует на все месяцы: при выборе совокупного плана отсутствующий месяц не подменяется прежним поартикульным планом. Сценарная модель не влияет на главную.
- История склеек импортируется локально по ключу `date + product_id`. Пустой код — явная группа «Без склейки», отсутствие записи до первой даты — неизвестный состав; в многодневных расчётах группа разрешается отдельно для каждого дня.
- Рост локальной базы требует диапазонных выборок, кэша агрегатов и виртуализации таблиц.
- План ДРР и рекламного бюджета пока не имеет единого месячного источника.
- ABC и бизнес-роли на странице рентабельности являются периодными относительными классификациями: ABC использует границы накопленной доли 80/95, а роль рассчитывается внутри склейки по классам выручки, положительной ЧП и рекламных расходов.
- Подтверждённая рекламная атрибуция точек входа сейчас не реализована и не назначена будущей версии.
- Массовое объединение поисковых запросов WB и продавца остаётся замороженным backlog из-за объёма данных.
- Доля на странице «Конкуренты» ограничена составом загруженного файла и не должна называться долей всего рынка; наш ассортимент определяется по совпадению WB ID со справочником.
- География поддерживает общий фильтр «Все / FBO · Склад WB / FBS · Маркетплейс». FBO и FBS собираются из соответствующих локальных и нелокальных колонок отчёта только внутри расчётов; локальность не является UI-срезом. Сумма и прибыль по типу остаются пропорциональной атрибуцией к общему `orders_total`, потому что исходный отчёт не содержит раздельных денежных полей; покрытие FBO/FBS показывается отдельно. Нулевые колонки остатков этого отчёта больше не импортируются и не участвуют в аналитике географии.
- Отчёт «Рынок» не содержит измерений кабинета, категории, бренда или товара; «Отчётность» не применяет к нему фиктивные entity-фильтры и не распределяет рынок по кабинетам.
- Backend-пилот V5 «Рынок» ограничивает исходный файл 10 MiB, один staging-вызов 500 строками, партию 50 000 строками и серверную выборку пятью годами. XLSX/CSV подключены к Import UI через `read-excel-file` в browser Web Worker; сервер сохраняет исходник, повторно валидирует строки и публикует партию атомарно. Перед повторной передачей неопубликованной партии staging и прежние ошибки очищаются серверной транзакцией, исходник сохраняется; опубликованные партии сбросить нельзя. Importer может скачать исходник собственной/разрешённой партии, admin — любой доступной партии; доступ дополнительно ограничен RLS приватного bucket. Ручная приёмка в авторизованном браузере ещё не выполнена.
- Кабинетные ограничения уже возвращаются в UI-контракте доступа, но пока не используются для клиентской фильтрации: единственная non-admin страница «Рынок» не имеет измерения кабинета. Каждая следующая страница открывается ролям только после переноса её данных и серверного применения кабинетного RLS; local-first страницы non-admin скрыты.
- `npm audit --omit=dev` фиксирует одну high-уязвимость унаследованной production-зависимости `xlsx@0.18.5` без автоматического исправления в npm. Новый UI-путь «Рынка» её не использует; `xlsx` остаётся в legacy V4 и в read-only сверке доверенного контрольного файла.

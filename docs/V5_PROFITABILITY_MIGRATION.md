# Рентабельность V5

Проверено: **20 сентября 2026**. Этап: источники и формулы V4 воспроизводимо проверены; parser-контракт, серверный lifecycle фактов, bounded read API и server-only UI реализованы в dev V5. Постоянная рабочая публикация и подтверждённые проценты постоянных расходов ещё требуют функциональной приёмки.

## Фактический V4-контракт

- Импорт хранит один `ProfitabilityRecord` на `period_start + period_end + product_id`. В фактическом backup все периоды однодневные.
- `profit_revenue` — выручка.
- Поле `actual_profit` названо неточно: на странице это **валовая прибыль после расходов маркетплейса**, но до кабинетных постоянных расходов.
- При наличии разбивки V4 игнорирует переданную валовую прибыль и повторно считает `revenue - cost - agent_fee - logistics_cost - marketing_cost - storage_cost`.
- `actual_margin` — валовая маржинальность. Агрегат считается только как `sum(gross_profit) / sum(revenue) × 100`, не как среднее процентов строк.
- Чистая прибыль равна `gross_profit - revenue × fixed_expense_percent / 100`; рентабельность равна `net_profit / revenue × 100`.
- Процент постоянных расходов задаётся отдельно по `month + cabinet`. В local-first режиме он находится в `localStorage` под `profitability_extra_expenses_v2` и не входит в `data` V4 backup.
- Те же деньги дублируются в `DailyMetrics`; страница предпочитает `ProfitabilityRecord`, а metric-слой использует только как fallback. Серверная модель не должна сохранять два конкурирующих источника истины.

## Целевой контракт

1. Версионный факт имеет зерно `date + product + cabinet`, сохраняет исходник в private Storage, использует общий import-driven resolver и last-row правило V4 для точного повтора ключа.
2. Денежные компоненты хранятся раздельно: `revenue`, `cost`, `agent_fee`, `logistics_cost`, `marketing_cost`, `storage_cost`; `gross_profit` и `gross_margin` вычисляются сервером. Сообщённые файлом прибыль/маржа служат проверкой расхождения.
3. Постоянные расходы — отдельная версионная настройка `month + cabinet + percent`. Отсутствие значения означает «не задано», а не автоматически 0%. До явного переноса настройки чистая прибыль и рентабельность должны возвращаться `null`/«—».
4. `marketing_cost` из отчёта рентабельности — компонент его валовой прибыли. `ad_spend` XWay остаётся отдельной рекламной метрикой; при совпадающем покрытии они не суммируются и не смешиваются без отдельной сверки методологии.
5. Read API пересчитывает все проценты из агрегированных сумм, применяет датированные склейки и ограничивает период, фильтры, сортировку и пагинацию. Server-only UI не использует `data/store` или локальный `profitStore`.

## Реализованный серверный этап

Миграция `20260916030000` создаёт `analytics.profitability_metric_versions` с version order и кабинетным RLS. Каждая партия хранит private `.xlsx`, проходит hash-идемпотентность и staging до 500 000 строк, полностью валидируется до создания товаров и публикуется атомарно. Обязательные денежные компоненты сохраняются отдельно; `gross_profit` и `gross_margin` являются generated columns и не доверяют переданным итогам файла. Сообщённые прибыль и маржа сохраняются отдельно для диагностики. Функция публикации имеет локальный лимит 120 секунд для полного кабинетного файла, не меняя общий API-лимит.

Удалённый `profitability_smoke.sql` подтвердил рассчитанные 500 ₽ валовой прибыли и 50% маржи на контрольной строке, блокировку партии с неверной датой, отрицательным количеством и отсутствующим компонентом, отсутствие созданного товара после ошибки и удаление версии при rollback. Вся проверка завершилась откатом транзакции.

## Реализованный read/UI этап

Миграции `20260920032000` и `20260920033000` добавляют private current-view, bounded RPC периода, фильтров, KPI, дневной динамики и пагинированных строк. Месячные проценты постоянных расходов хранятся по кабинету и меняются только администратором. Пока процент отсутствует хотя бы для одного затронутого кабинета-месяца, `net_profit` и `profitability` возвращаются как `null`, а не как ложный ноль.

V5 Import UI разбирает `.xlsx` в Web Worker, автоматически распределяет строки по первой цифре артикула продавца (3/4 — «Светпланет», 5 — «Ледситипро») и создаёт отдельные кабинетные партии. Страница «Рентабельность» читает только серверные RPC и не импортирует `data/store` или локальный `profitStore`.

Повторный remote smoke подтвердил публикацию, вычисляемые gross-метрики, nullable net-метрики до настройки, admin-only месячный процент, bounded-чтение, отклонение ошибочной партии и rollback. Тестовые данные полностью откатились.

## Открытый gate

- опубликовать контрольный реальный файл через браузер и принять server-only страницу;
- получить от владельца подтверждённые проценты постоянных расходов по каждому кабинету и месяцу. Нулевые значения по умолчанию не мигрируются как факт.

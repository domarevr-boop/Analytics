# Импорт-управляемый реестр товаров Analytics MVP

**Статус:** фактический контракт V4 перенесён в серверную модель V5; bootstrap V4 сохранён только как необязательный исторический инструмент. Проверено 11 сентября 2026.

## Назначение

Реестр является общим серверным состоянием идентичностей для Dashboard, импорта, планирования, рентабельности, фильтров и изображений. Он развивается из рабочих импортов и не требует предварительной постоянной загрузки полного каталога. Товар не удаляется из реестра из-за отсутствия в новом отчёте.

## Карточка товара

- стабильный внутренний `product_id`;
- артикул продавца `sku`;
- артикул Wildberries `wb_sku`;
- исторические артикулы и альтернативные обозначения `aliases`;
- название и категория;
- бренд, кабинет и склейка на выбранную дату;
- статус `active` или `archived`;
- источник последнего изменения и дата обновления.

## Правила импорта

1. Каждый новый артикул из любого источника обязан попасть в реестр.
2. В пределах выбранного кабинета проверяются точный SKU, его каноническая форма без Excel-суффикса `.0`, сохранённый алиас и WB ID.
3. Встреченные варианты написания сохраняются как алиасы и не удаляются последующими импортами.
4. Импорт дополняет пустые поля карточки; ручное редактирование имеет приоритет.
5. Метрики продолжают ссылаться на стабильный `product_id`.

В V5 идентификаторы сопоставляются только внутри кабинета. Если валидная строка не соответствует существующему товару, сервер создаёт его с `data_source = import`, сохраняет batch-lineage и исходные варианты идентификаторов как алиасы. Если seller SKU и WB ID указывают на разные существующие товары, автоматического объединения не происходит: партия отклоняется как неоднозначная.

## Ручная работа

На странице «Справочник» доступны поиск и фильтры, контроль полноты карточек, изменение SKU и WB ID, категории, бренда, кабинета, склейки, алиасов и статуса.

## История склеек

Склейка хранится отдельными записями `date + product_id`, импортированными из отчёта «Склейки». Пустой код означает явную группу «Без склейки». Для даты используется последняя известная запись, действующая не позже этой даты; если до даты нет ни одной записи, состав считается неизвестным и не подменяется «Без склейки».

В аналитическом периоде товар учитывается в каждой группе, в которой он состоял на соответствующую дату. Поэтому при смене склейки внутри периода одна карточка может попасть в несколько групп, а состав каждой группы описывает фактический дневной срез. Ручное изменение в справочнике создаёт запись истории с датой «Действует с».

Серверная модель V5 находится в `core.products`, `core.product_aliases`, `core.product_groups` и `core.group_membership_versions`. Она запрещает два состояния товара на одну дату, проверяет совпадение кабинета товара и склейки и хранит ссылку на исходную партию. Общая группа V4 «Без склейки» при переносе должна стать отдельной явной группой каждого кабинета; до первой датированной записи resolver возвращает неизвестный состав.

## Контрольный срез V4

Потоково проверена резервная копия `analytics-v4-backup-2026-09-06.json`: версия `v4.0`, экспорт `2026-09-06T15:49:11.425Z`, размер 406 210 120 байт, SHA-256 `239D202611E14F7B934F82D081DD73C794B720A7D1FDBC0C6C2ADBF7A61844E1`. Файл хранится вне Git и в V5 не загружался.

В копии находятся 2 кабинета, 3 бренда, 33 строки групп, 1 068 строк товаров, 1 068 текущих memberships и 1 458 датированных состояний. Точные identity образуют 536 потенциальных канонических товаров: 1 056 строк входят в 524 компоненты дублей, максимальный размер компоненты — 4. При этом обнаружены 2 компоненты с несколькими WB ID и 4 с несколькими правдоподобными seller SKU; они требуют разбора. Шесть строк товаров не имеют кабинета, две группы не имеют кабинета, но битых ссылок product/group и повторов `date + product_id` в истории нет. 1 058 исторических строк содержат явное состояние «Без склейки».

Команда `npm run backup:v4:inspect -- "<путь-к-backup.json>"` повторяет подсчёт потоково, не возвращает строки каталога и не загружает весь файл в память.

Команда `npm run backup:v4:prepare-directory -- "<путь-к-backup.json>"` формирует локальный манифест `.v5-local/directory-bootstrap.json`; каталог `.v5-local` исключён из Git. Dry-run контрольной копии создал 528 однозначных товаров, 2 используемых бренда, 14 категорий, 33 кабинетные группы, 6 алиасов и 1 441 датированное состояние склейки. Все ссылки принятой части замкнуты, ключи товаров и `product + date` уникальны. В очередь разбора попали 8 identity-компонент: 4 из-за отсутствующего/неоднозначного кабинета, 2 с несколькими WB ID и 4 с несколькими правдоподобными seller SKU; одна компонента может иметь несколько причин. Все 17 строк истории этих компонент сохранены в `groupHistoryCandidates`, но пока не переносятся в принятую часть. Манифест не записывался в Supabase.

Команда `npm run backup:v4:prepare-directory-review` создаёт два игнорируемых Git артефакта: `.v5-local/directory-review.md` с кандидатами и их отложенной историей и `.v5-local/directory-review-decisions.json` с пустыми решениями. Шаблон содержит SHA-256 исходного backup и отдельный fingerprint всей очереди разбора. Для каждой компоненты допустимы только явные действия `merge`, `split` или `exclude`; незаполненный шаблон не является решением и не участвует в публикации. Контрольный отчёт содержит 8 компонент. Скрипт отказывается перезаписывать существующий отчёт, поэтому повторная генерация требует нового пути или осознанного переноса локального черновика.

Команда `npm run backup:v4:validate-directory-review` проверяет hash/fingerprint, полноту всех решений, точное разбиение legacy ID, кабинет, имя и статус товара, отсутствие конфликтов seller SKU/WB ID/алиасов, обязательное объяснение исключения и принадлежность исторической склейки кабинету. Пока решения не заполнены, команда обязана завершаться ошибкой `unresolved_decision: 8`; это защитное поведение, а не сбой.

## Серверный путь V5

Основной рабочий путь реализован миграцией `20260911019000`: после полной серверной валидации geography-партии он разрешает или создаёт товары, сохраняет алиасы и назначает новому товару датированное «Без склейки». Удалённый rollback-smoke подтвердил создание, канонизацию `.0`, повторное разрешение, алиас и отсутствие записей от ошибочной партии.

Транзакционный приём подготовленного V4-манифеста из миграции `20260908009000` остаётся дополнительным инструментом для разового исторического переноса. Он не является зависимостью запуска страниц и по умолчанию выключен флагом `VITE_V5_DIRECTORY_BOOTSTRAP_ENABLED=false`.

Миграция `20260908010000` добавляет безопасный контракт чтения: `v5_directory_snapshot` возвращает не более 500 доступных пользователю товаров, ищет по основным идентификаторам и алиасам и определяет последнюю известную склейку на указанную дату; `v5_directory_filters` возвращает только доступные кабинеты и фактически используемые категории/бренды. Remote smoke и db lint прошли. Типизированный frontend-адаптер проверяет структуру ответа и клиентские пределы, но страница на RPC пока не переключена, а флаг `VITE_V5_DIRECTORY_BACKEND_ENABLED` остаётся выключенным.

Следующий этап — подключать этот resolver к каждому товарному импорту, начиная с «Географии», и включать серверные страницы после публикации соответствующего источника и browser-приёмки. Восемь старых bootstrap-неоднозначностей больше не блокируют V5; к ним возвращаются только если понадобится массово восстановить исторические товары и склейки, которых нет ни в одном рабочем импорте.

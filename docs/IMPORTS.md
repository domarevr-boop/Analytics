# Импорт данных Analytics MVP

**Статус:** канонический контракт импорта и дат.

## Формат даты

- В хранилище даты записываются только как `YYYY-MM-DD`.
- Даты отчёта в формате `ДД.ММ` разрешены только вместе с явно выбранным в окне импорта годом отчёта.
- Excel-даты читаются из исходного числового кода без преобразования через часовой пояс JavaScript.
- Строковые даты нормализуются, затем проходят строгую календарную проверку.
- Неизвестная, невозможная или перевёрнутая дата блокирует весь импорт до изменения данных.
- Журнал импорта получает фактические минимальную и максимальную даты успешно проверенного набора.

## Источники

### WB Воронка

- Обязательны SKU и дата в файле.
- Для источника `WB Воронка` заголовки `Показы`, `Переходы в карточку`, `Добавления в корзину` и `Заказы` всегда записываются в метрики воронки, даже если такие же заголовки используются в отчёте «Точки входа».
- При импорте SKU нормализуется и связывается с существующей карточкой товара по SKU, WB ID и известным алиасам. Это предотвращает разнос показов, кликов и корзин по разным строкам Dashboard.
- Сопоставление SKU, WB ID и алиасов выполняется внутри кабинета. Совпавший идентификатор из другого кабинета не считается тем же товаром.
- Повторный импорт заменяет поля воронки только для фактически присутствующих в файле пар `дата + товар`. Отсутствующие внутри периода даты не обнуляются.
- Для каждой пары `дата + товар` заменяются только те метрики, колонки которых действительно распознаны в текущем файле. Частично распознанный отчёт не обнуляет показы, клики или другие отсутствующие поля.
- Замена выполняется только для точного товара из строки импорта и не распространяется на алиасы, склейки и похожие SKU. Суффиксы артикула, включая значения в скобках, считаются частью самостоятельного SKU.
- Строка без единой распознанной метрики не считается успешно импортированной.
- Поддерживаются Excel, CSV и строковые форматы дат, распознаваемые общей нормализацией.
- Если файл был импортирован до исправления сопоставления колонок, повторно загружается только затронутый диапазон дат. Импорт без сохранённых показов и кликов не может быть восстановлен автоматически.
- `nm_id` и русские варианты `Артикул WB` сохраняются как отдельный `wb_sku` и обновляют уже существующий товар по артикулу продавца.
- При восстановлении данных в чистой сессии облачная таблица `daily_metrics` читается постранично в стабильном порядке `дата + product_id`; серверный лимит Supabase больше не обрезает показы, клики и производный CTR.
- Главная страница объединяет строки воронки всех связанных карточек одного товара по SKU продавца, WB ID и историческим алиасам. Показы и клики попадают в исходный кабинет, категорию и склейку, даже если импорт ранее создал временную карточку без кабинета.

### XWay Реклама

- Обязателен SKU.
- Если дата присутствует в файле, используется она.
- Если даты нет, пользователь обязан выбрать единую дату отчёта до импорта.
- Повторный импорт заменяет рекламные поля только для фактически присутствующих пар `дата + товар`; пропущенные даты и данные другого кабинета сохраняются.

### Рентабельность

- Обязателен SKU.
- При импорте финансовый факт сохраняется одновременно в реестре отчётов и в дневных метриках по ключу `дата + SKU`. Это позволяет верхним KPI агрегировать месяц, а таблице и мини-графикам — независимый выбранный диапазон дат.
- Если для SKU и даты отсутствует строка отчёта рентабельности, дневные показатели прибыли и рентабельности принимают значение `0`; они не вычисляются из данных другого источника.

### Инварианты сопоставления колонок

- Одинаковый заголовок в разных источниках может иметь разный смысл. Глобальное сопоставление для таких колонок запрещено.
- `Показы`, `Переходы в карточку`, `Добавления в корзину` и `Заказы` из `WB Воронки` записываются только в поля воронки. Одноимённые значения отчёта «Точки входа» записываются только в поля точек входа.
- При добавлении нового источника его словарь заголовков и обязательные поля задаются отдельно от существующих источников.
- Строгие обязательные поля отчёта: `Выручка`, `Валовая прибыль с учетом расходов маркетплейса`, `Итоговая маржинальность, %`. В предпросмотре перед импортом отображаются именно эти три значения для проверки сопоставления.
- Если в файле присутствует разбивка расходов, валовая прибыль при импорте пересчитывается как `Выручка − Себестоимость − Агентское вознаграждение − Логистика − Реклама − Хранение`; итоговые колонки прибыли и маржинальности остаются контрольными значениями отчёта.
- Выручка и итоговая маржинальность из этого отчёта — источник факта для страницы рентабельности, Dashboard и финансовых графиков.
- Чистая прибыль рассчитывается как `Выручка отчёта × (Маржинальность отчёта, % − Постоянные расходы месяца, %) / 100`.
- Для исторических записей, в которых импортирована валовая прибыль, но отсутствует маржинальность, маржинальность восстанавливается как `Валовая прибыль / Выручка × 100`.
- Поддерживаются `date`, `period_start` и `period_end`, включая русские варианты заголовков.
- Для дневной колонки допустим формат `ДД.ММ`: перед импортом пользователь подтверждает год отчёта.
- Если периода нет в файле, пользователь обязан выбрать начало и конец периода.
- Конец периода не может быть раньше начала.
- При наличии записей рентабельности за выбранный период их выручка, прибыль и маржинальность используются в Dashboard, таблице и графиках вместо повторного расчёта из расходов.

### План

- Поддерживается двухуровневая Excel-шапка: первая строка содержит месяцы, вторая — показатели каждого месяца.
- Год берётся из выбранного месяца на странице планирования; при переходе последовательности с декабря на январь год увеличивается.
- Из файла используются только `Код`, `Среднее шт/день` и `Чек`.
- Числовые Excel-ячейки читаются по исходному числовому значению, а не по отображаемому форматированию.
- Русские десятичные запятые, проценты, обычные и неразрывные пробелы нормализуются до чисел.
- Каждый SKU и месяц сохраняются как отдельная запись плана; повторный импорт обновляет существующую запись.
- Импорт сохраняется пакетно и сразу используется страницей планирования, Dashboard и основной таблицей.
- План заказов в штуках рассчитывается как `Среднее шт/день × количество дней в месяце`.
- План заказов в рублях рассчитывается как `Заказы, шт × Чек`.
- Плановая выручка рассчитывается как `Заказы, руб × % выкупа`.
- Плановая чистая прибыль рассчитывается как `Выручка × Рентабельность`.
- `% выкупа` и `Рентабельность` задаются отдельно для каждого месяца, сохраняются в месячных записях и применяются ко всем SKU этого месяца.
- Сообщение об успешном импорте показывается только после завершения постоянного сохранения месячных записей.
- Месячные планы сохраняются в IndexedDB и синхронной резервной копии `localStorage`; при запуске резервная копия восстанавливает план, если основное хранилище не вернуло записи.

## Предпросмотр

## Страница импорта

- Полная хронология загрузок в интерфейсе не отображается.
- Для каждого типа отчёта показывается только последний загруженный файл, его период, число строк, время и статус.
- Нижняя сводка покрытия строится по фактически сохранённым данным для воронки, рекламы, рентабельности, географии, точек входа, поисковых запросов и плана.
- Для быстрого открытия страницы периоды покрытия источников восстанавливаются из журнала успешных импортов; страница не обходит все строки тяжёлых аналитических наборов.
- Отсутствующий источник остаётся в таблице со статусом «Отчёт ещё не загружен».

До подтверждения интерфейс показывает:

- минимальную и максимальную дату;
- количество строк с определённой датой;
- количество строк с ошибочной датой;
- блокирующее состояние, если покрытие определить нельзя.

## Правило для новых источников

### Отзывы WB / «Клиентский опыт»

- Это единственный серверный источник текущей версии; остальные отчёты остаются локальными.
- Обязательные поля: `Кабинет`, `ID отзыва`, `Дата`, `Количество звезд`.
- Товар сопоставляется по `Артикул WB`, затем по `Артикул продавца` и алиасам локального справочника.
- Исходный файл временно хранится в приватном Supabase Storage и удаляется только после серверной сверки всех строк.
- Контрольная формула: `всего строк = текстовые + пустые + дубликаты + отклонённые`.
- Дубликаты определяются по `источник + кабинет + ID отзыва`; повторный импорт не создаёт повторные отзывы или пустые оценки.
- Детальный контракт и процедура отката описаны в [CLIENT_EXPERIENCE.md](CLIENT_EXPERIENCE.md).

### Поисковые запросы WB

- Данные хранятся в отдельном наборе `search_queries`.
- Уникальный ключ: `date + query + category`.
- Повторный импорт обновляет совпавшую запись.
- Даты без года проходят общий предпросмотр и получают явно выбранный год отчёта.

### История склеек

- Источник распознаётся по колонкам даты, артикула продавца или WB и `Склейка`/`Код склейки`.
- Обязательный ключ — `date + product_id`; повторная строка с тем же ключом блокируется как дубликат до записи.
- Пустой код сохраняется как явная группа «Без склейки», а не как неизвестный состав. Для каждой даты импорт сначала сопоставляет артикул со справочником и только затем записывает историю.
- Между датами действует последняя известная запись. До первой записи состав неизвестен и не считается «Без склейки».
- На странице «Справочник» поле «Состав на дату» показывает состояние на выбранную дату; при ручном изменении используется дата «Действует с».
- Для многодневной аналитики состав определяется по каждому доступному дню. Если товар сменил склейку в периоде, он участвует в соответствующих группах в разные даты; это не ошибка дублирования.
- История хранится локально в IndexedDB и не отправляется в Supabase вместе с облачным контуром отзывов.
- V5 содержит пустую серверную модель `core.products`, `core.product_aliases`, `core.product_groups` и `core.group_membership_versions`. Seller SKU, WB ID и алиасы уникальны только внутри кабинета; `date + product_id` остаётся уникальным ключом состояния. Серверный resolver повторяет подтверждённую семантику V4. Атомарный bootstrap и admin-only Import UI подготовлены, но постоянный перенос рабочих строк заблокирован до решения 8 неоднозначных компонент и доказанного restore.

### География заказов

- Обязательные поля: `Дата`, `Артикул продавца`, `Регион` или `Кластер`, `Итого заказов, шт`.
- Для сквозного разделения заказов поддерживаются колонки `Заказы со склада WB локально, шт`, `Заказы со склада WB не локально, шт`, `Заказы Маркетплейс локально, шт` и `Заказы Маркетплейс не локально, шт`.
- Колонки остатков географического отчёта больше не импортируются: источник отдаёт в них нулевые значения, а складская обеспеченность анализируется в профильных источниках.
- В интерфейсе FBO («Склад WB») складывает две колонки WB, FBS («Маркетплейс») — две колонки Маркетплейса; локальная/нелокальная детализация не является пользовательским фильтром.
- Географический отчёт содержит разрез FBO/FBS в штуках. Сумма заказов, чистая прибыль и воронковые показатели при выборе типа распределяются пропорционально выбранным заказам к общему `Итого заказов, шт` товара за дату; это оценочная атрибуция, а не раздельные исходные деньги.
- Импорт и хранение остаются локальными; отсутствие или расхождение FBO/FBS с общим количеством не должно обнулять `Итого заказов, шт`, а страница показывает покрытие разметки.

### Рынок

- Обязательные колонки: `Дата`, `Заказы рынок`, `Наши заказы`, `Заказы, шт, рынок`, `Заказы, шт, мы`.
- Поддерживаются дополнительные готовые показатели: `Наша доля`, `Наша доля в заказах`, `Средний чек, мы`, `Средний чек рынок`.
- В V4 данные хранятся локально в `market_dynamics`; уникальный ключ — `date`, повторный импорт даты заменяет строку.
- В V5 backend-пилот хранит каждую опубликованную версию даты с lineage партии. Текущей становится запись с наибольшим монотонным `version_order`; отмена партии раскрывает предыдущую опубликованную версию без физического удаления истории.
- Повторная попытка той же неопубликованной партии сначала атомарно очищает прежние staging-строки и ошибки, затем передаёт весь нормализованный набор заново. Исходный файл сохраняется; опубликованная партия защищена от такого сброса.
- Серверный журнал возвращает не более 50 доступных партий; UI показывает последние 20 с периодом, статусом, принятыми/отклонёнными строками, количеством ошибок и попыток, а также фактом наличия исходника. Importer видит собственные/разрешённые партии, admin — все.
- По кнопке «Ошибки» UI запрашивает до 100 построчных записей выбранной партии: лист, строку, колонку, код, сообщение и исходное значение. Серверный предел — 200; доступ проверяется отдельно для партии, прямое чтение `ingest.import_errors` клиенту не требуется.
- По кнопке «Скачать» importer получает сохранённый исходник собственной/разрешённой партии, admin — доступной ему партии. RPC журнала возвращает object path только после проверки роли и видимости партии, а само чтение повторно ограничено RLS приватного bucket; публичные URL не создаются.
- По кнопке «Этапы» UI запрашивает до 100 событий жизненного цикла выбранной партии: время, статус, серверное сообщение и технические параметры. Серверный предел — 200; UUID исполнителя и прямой доступ к `ingest.import_events` UI не выдаются.
- V5 принимает `.xlsx`/`.csv` до 10 MiB, staging-пакеты до 500 строк и партии до 50 000 строк. `read-excel-file` разбирает XLSX в browser Web Worker с лимитом 60 секунд; CSV разбирается там же. После SHA-256 исходник сохраняется в private Storage до staging. Сервер проверяет ISO-даты, обязательные числа/целые, диапазоны, повторы дат и публикует только целиком валидную партию.
- Excel-доли хранятся в ячейках как доли единицы. Транспортная нормализация восстанавливает процентные пункты по совпадению с обязательными числителем и знаменателем; сама аналитическая доля по-прежнему пересчитывается из суммарных числителя и знаменателя.
- В V5-only режиме страница «Рынок» получает границы и не более пяти лет дневных данных через RPC. Ошибка серверного чтения показывается пользователю; локальный набор V4 не используется как скрытый fallback.
- В V5 роль `importer` видит на странице импорта только серверный источник «Рынок». Файл, который не распознан как этот источник, блокируется до локального mapper/записи; локальные журналы, покрытие, отзывы и конкуренты этому пользователю не показываются. Полный legacy-импорт временно остаётся только у `admin` до миграции соответствующих источников.
- Страница V4 и RPC V5 пересчитывают итоговые доли и средние чеки из суммарных числителей и знаменателей; готовые средние чеки источника сохраняются только для дневной точки.
- Этот источник задаёт средний чек для оценки суммы заказов на странице «Поисковые запросы» и не зависит от отчёта «Динамика ниши».

### Динамика ниши

- Источник сохранён только для совместимости с ранее загруженными локальными данными; отдельной аналитической страницы и активного потребителя у него больше нет.
- Данные сохраняются как ежедневные снимки месячного отчёта.
- Уникальный ключ: `date + category + subject`.
- Значения разных дат не суммируются между собой на странице аналитики.

### Конкуренты

Полный контракт страницы и расчётов: [COMPETITORS.md](COMPETITORS.md).

- Один Excel-файл должен содержать четыре распознаваемых листа: заказы и воронка, поисковые запросы, склады и остатки, ежедневные позиции TOP-50.
- Все четыре листа проверяются до записи и заменяются одной атомарной транзакцией. Импорт не меняет другие локальные источники и серверные отзывы.
- Числовые ячейки читаются по сырым значениям Excel, а не по отображаемому формату: пользовательское сокращение тысяч или миллионов в формате ячейки не должно менять сумму, цену, заказы и показы. Числовые проценты Excel переводятся из долей в процентные пункты, текстовые проценты читаются как показано в файле.
- Наборы связываются по нормализованной дате и артикулу WB. Даты `ДД.ММ` получают год из листа с полной датой либо из подтверждённого года отчёта.
- Уникальные ключи: `date + wb_article` для воронки и позиций; `date + wb_article + query` для запросов; `date + wb_article + region + warehouse` для остатков.
- Страница считает долю только внутри загруженного конкурентного среза. Наш ассортимент определяется совпадением артикула с `products.wb_sku`.
- Для остатка на последнюю дату используется строка склада `Маркетплейс`, если она присутствует; иначе суммируются детальные склады. Это исключает двойной счёт агрегата и складских строк.
- `% выкупа` агрегируется как взвешенное заказами исходное значение. Колонки `Выкупы` и `Заказы` не используются для обратного расчёта процента, поскольку могут описывать разные когорты.
- Повторённая по артикулам глобальная частотность одного поискового запроса объединяется по нормализованному тексту и не суммируется; интерфейс отдельно показывает число карточек с этим запросом.
- В V5 исходник сохраняется в private Storage, четыре секции проходят staging и повторную серверную валидацию и публикуются только одной полной версией. Bounded read API и RPC журнала применены в dev-контуре и прошли remote smoke. Новый `.xlsx` parser работает в browser Web Worker без `xlsx@0.18.5`; Import UI показывает preview, прогресс, ошибки, этапы и доступный private-исходник. Путь закрыт `VITE_V5_COMPETITORS_IMPORT_ENABLED=false`; `.xls` необходимо пересохранить в `.xlsx`. По решению владельца V5 сохраняет фактические даты Excel; `backup:v4:compare-competitor-parser -- "<файл>" <год> --accept-excel-dates` допускает только известный сдвиг legacy V4 ровно на день назад. Текущая страница остаётся V4-only до разрешённой серверной сверки контрольного payload, ручной приёмки и постоянной партии.

Новый источник должен использовать `normalizeImportDate` и общий предварительный контроль до изменения товаров, метрик, отчётов или журнала импорта. Нельзя сохранять исходную строку даты напрямую.

Все импорты и изменения планов должны проходить через последовательную очередь сохранения. Параллельные записи одного снимка состояния запрещены, чтобы более ранняя операция не могла перезаписать более новую при перезагрузке страницы. Очередь сохраняет только дельту — добавленные, изменённые и удалённые записи — а не весь исторический снимок. После подтверждённого импорта повторное сохранение того же состояния не запускается.

Локальная транзакция сохраняет атомарно только реально изменённые наборы данных. Все операции добавляются в IndexedDB без последовательного ожидания каждой строки, а интерфейс завершает импорт после подтверждения всей транзакции. Составные ключи должны строиться по именам полей клиентской модели (`entityId`, `entityType` для планов), а не по SQL-именам колонок.

## Производительность и целостность

- Номер версии `analytics-db` может только увеличиваться. Текущая схема — 11; откат frontend не должен пытаться открыть существующую IndexedDB с меньшей версией; неиспользуемые хранилища прежней опубликованной схемы сохраняются до отдельной доказанной миграции очистки.
- Импорт сохраняет и сравнивает только наборы, относящиеся к выбранному источнику. Небольшой отчёт не должен копировать или обходить историю поисковых запросов, географии и других независимых источников.
- Связи SKU, WB ID и алиасов индексируются один раз на операцию импорта. Повторное построение полного товарного индекса для каждой строки запрещено.
- Финансовые поля точек входа пересчитываются только после импорта воронки, рекламы, рентабельности или самих точек входа.
- Переход между страницами, скрытие вкладки и перезагрузка не запускают полный снимок IndexedDB. Все подтверждённые изменения сохраняются непосредственно в операции, которая их создала.
- Представления крупных наборов данных кэшируются до изменения соответствующего источника. Обычный рендер или смена страницы не должны повторно клонировать сотни тысяч строк.
- Инициализация сохраняет только хранилища, изменённые миграцией или нормализацией; фоновая полная запись после показа интерфейса запрещена.
- Пока открыта страница импорта, вычисления Dashboard не монтируются и не реагируют на уведомления хранилища.
- Перед синхронным разбором файла интерфейс получает отдельный кадр для отображения состояния загрузки.
- Покрытие источников рассчитывается слиянием валидных диапазонов дат. Интерфейс не разворачивает диапазоны в массив дней и игнорирует повреждённые даты журнала, поэтому аномальная запись не может заблокировать страницу импорта.
- В блоке покрытия рядом с каждым отчётом показывается оценочный объём его записей. Это не размер файла Excel и не полный размер IndexedDB: показатель вычисляется по репрезентативной выборке строк, поэтому не создаёт тяжёлый обход локальной базы.

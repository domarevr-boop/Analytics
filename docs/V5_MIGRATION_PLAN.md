# План перехода Analytics V4 → V5

Обновлено и проверено: **7 сентября 2026**.

## Цель и границы

V5 переносит хранение, импорт и воспроизводимые расчёты основных отчётов из браузерной IndexedDB в отдельный Supabase/PostgreSQL-контур. V4 остаётся рабочей production-версией до отдельного принятия V5. На этапе подготовки запрещены миграции в действующую БД V4, публикация V5 на рабочий URL и массовый перенос страниц.

Целевой путь каждого законченного сценария: **исходный файл → приватное исходное хранилище → серверная валидация и staging → идемпотентная запись нормализованных данных → версионированный расчёт/RPC → React-страница**. Клиент загружает файл и читает готовые данные, но не является источником истины и не выполняет массовый merge.

## Подтверждённое исходное состояние

- Production-код V4 зафиксирован в `main` на `8dd7db8`; V5 создана от той же ревизии в ветке `v5/backend-foundation` и отдельном worktree `C:\Users\vipdo\Documents\test\Analytics-v5`.
- V4 хранит 24 набора IndexedDB схемы 11, значительную часть вычислений выполняет в TypeScript и подписывает React через in-memory store. Настройки интерфейса и отдельные резервные значения также используют `localStorage`.
- Текущий импорт распознаёт 12 типов источников. Большинство файлов парсится и сливается в браузере; ключи и владение полями зависят от источника.
- Имеющийся `CloudRepository` — неполный эксперимент: он поддерживает только часть наборов, читает большие таблицы в frontend и не содержит историю склеек, совокупные планы, географию, точки входа, поиск, рынок и конкурентов. Он не принимается за основу V5 без переработки.
- Серверный CX-контур использует Auth, RLS, приватный Storage, журнал партий, дедупликационный реестр, версионированные словари/модели, batch-RPC, агрегаты и пагинацию. Однако файл разбирается, нормализуется и лемматизируется в браузере, а записи выполняются несколькими клиентскими запросами с компенсирующим удалением при ошибке. Для остальных модулей это образец отдельных механизмов, но не готовый универсальный backend.
- Все пользователи приложения сейчас фактически должны быть администраторами. Роли viewer/importer отсутствуют. Фоновых заданий и планировщика в репозитории не обнаружено.
- GitHub Actions публикует только push в `main` и полностью заменяет ветку `gh-pages`; ветка V5 сама не публикуется. Для одновременного сохранения V4 и `/Analytics/v5/` перед релизом потребуется составной deployment.
- Локальная Supabase недоступна: Docker на машине не установлен. Отдельный облачный проект V5 создан 6 сентября 2026, отличается от V4; CLI связан только с ним, foundation применён и проверен через журнал миграций, db lint, health RPC и anon REST.

## Целевая модель backend

1. **Источники и сырой слой.** Реестр источников и их версий; приватный bucket исходных файлов; `import_batches` с хешем, владельцем, периодом, статусом, счётчиками и ошибками; staging/raw-записи с исходной строкой и номером строки. Исходный файл не удаляется автоматически после успешной загрузки: срок хранения задаётся политикой.
2. **Единые справочники.** Стабильные идентификаторы кабинета, товара, SKU/WB ID и алиасов; категории, бренды и датированная история склеек. Неоднозначное сопоставление попадает в очередь разбора, а не объединяется эвристически.
3. **Факты по источникам.** Отдельные таблицы с естественными уникальными ключами и явным владельцем каждого поля. Повторный импорт обновляет только строки и поля своего источника; отсутствие колонки или даты не обнуляет чужие данные.
4. **Обработка.** Серверная функция/worker получает партию, валидирует схему и даты, пишет staging, выполняет transaction merge и контрольные счётчики. Неуспешная партия не становится видимой аналитике. Ручной запуск стабилизируется раньше API-автоматизации.
5. **Расчёты.** Версионированный каталог показателей фиксирует смысл, формулу, гранулярность, допустимые фильтры, владельца и ограничения. SQL views/RPC или materialized views возвращают только необходимые агрегаты и страницы данных. Перенос формулы выполняется без её изменения; методологическая правка создаёт отдельную задачу и новую версию.
6. **Доступ и аудит.** Минимальные роли `viewer`, `importer`, `admin`, RLS по разрешённым кабинетам, журнал действий и запрет service-role в браузере. Edge Functions используют service-role только на сервере.
7. **Надёжность.** Базовое резервное копирование БД и исходных файлов, регулярная проверка восстановления в отдельную среду, журнал ошибок и метрики партий. Конкретный механизм backup выбирается после проверки возможностей отдельного проекта V5.

## Контрольные данные

До переноса первого сценария формируется контрольный пакет:

- экспорт V4 из страницы «Разработка» и сохранённые исходные файлы;
- малые обезличенные fixtures для каждого источника: корректный файл, повтор того же файла, частичный набор колонок, дубликат, ошибочная дата, одинаковый SKU в разных кабинетах;
- контрольные SQL/TypeScript-агрегаты по нескольким датам, кабинетам, товарам и итогам;
- манифест с SHA-256 файлов, количеством входных/принятых/отклонённых строк и версией формулы;
- отчёт различий V4/V5 с объяснением каждого ненулевого отклонения.

## Этапы

Порядок страниц предварительный: фактическая ежедневная важность должна быть подтверждена владельцем перед этапом 4. Общие зависимости переносятся раньше страниц, даже если сами страницы важны.

### 0. Базовая фиксация и изоляция — код выполнен, облачный контур ожидается

- **Результат:** отдельные ветка/worktree V5; V4 не изменена; удалена наследованная CLI-привязка Supabase; V5 не публикуется; зависимости установлены, baseline собирается и проходит 59 тестов V4 и 13 инфраструктурных тестов V5.
- **Зависимости:** `origin/main` и чистая V4.
- **Модули:** Git, env, Supabase metadata, документация.
- **Проверка:** обе ветки созданы от одного исходного commit; V4 чистая; в V5 нет `.env*local` и `supabase/.temp`; workflow слушает только `main`; build успешен. Полный lint сохраняет известный baseline V4 — 27 ошибок и 26 предупреждений — и вынесен из этой изоляционной задачи.
- **Откат:** удалить worktree и ветку V5; V4 и production не затрагиваются.

### 1. Изолированный backend-фундамент — схема и доступ применены, recovery не завершён

- **Результат:** отдельный Supabase-проект V5, локально зафиксированная конфигурация, миграции схем `app/ingest/core/analytics`, роли, журнал доступа, закрытый bootstrap администратора и пустой private Storage; V4-проект не связан с worktree V5.
- **Зависимости:** проект, env, CLI link, базовая схема и первый проверенный admin готовы; роли и кабинетные ограничения прошли транзакционный smoke-test. Остались release-проверка реальными viewer/importer и выбранный механизм backup/restore.
- **Модули:** `supabase/`, `.env.example`, Auth/RLS, Edge Functions.
- **Проверка:** идентификатор проекта отличается от V4; destructive smoke-test выполняется только на V5; anon не читает данные, viewer не пишет, importer создаёт партию, admin управляет доступом.
- **Откат:** удалить отдельный V5-проект или пересоздать его; production V4 не меняется.

### 2. Универсальный ручной импорт

- **Результат:** загрузка исходника в Storage, журнал партии, staging, серверная валидация, атомарный merge, ошибки по строкам и повторный запуск без дублей.
- **Зависимости:** этап 1, утверждённые правила дат и source-field ownership из `IMPORTS.md`, решение по безопасному серверному XLSX parser вместо непроверенного переноса `xlsx@0.18.5`.
- **Модули:** Import UI, Edge Function/worker, `import_batches`, `import_files`, staging, аудит.
- **Проверка:** все fixtures; повтор идентичного файла не меняет факты; частичный файл не обнуляет чужие поля; failed batch не виден аналитике; исходник и лог доступны администратору.
- **Откат:** пометить/откатить конкретную партию через её lineage, не удаляя партии других источников.

### 3. Справочники и временные связи

- **Результат:** единый товарный каталог, кабинеты, категории, бренды, алиасы и история склеек с датой действия; очередь неоднозначных соответствий.
- **Зависимости:** этап 2 и контрольный экспорт V4.
- **Модули:** Справочник, product matching, фильтры, group history.
- **Проверка:** одинаковый SKU разных кабинетов не объединяется; WB ID и алиасы разрешаются детерминированно; склейка корректна на один день и многодневный период.
- **Откат:** версионированное исправление справочника/связи; факты сохраняют исходный lineage.

### 4. Пилот «Рынок»

- **Статус:** backend-контракт, Web Worker/parser, Import UI, транзакционная сверка реального V4-файла и V5-only чтение `MarketPage` через feature flag реализованы. Осталась ручная приёмка авторизованного UI и проверка downstream-потребителей.
- **Результат:** первый полный серверный сценарий от исходного файла до существующей страницы без изменения формул.
- **Почему он:** один естественный ключ `date`, небольшой агрегированный источник без зависимости от товарного справочника, при этом его средний чек используется поиском и его показатели — отчётностью.
- **Зависимости:** этапы 1–2.
- **Модули:** импорт `market_dynamics`, серверная таблица/RPC, `MarketPage`, связанные тесты.
- **Проверка:** транзакционные fixtures подтверждают суммы, штуки, доли, средние чеки, day/month aggregation, повторную версию, очистку незавершённого staging, откат и отклонение ошибок. Дополнительно `db:v5:smoke-market-file` сверяет parser V4/V5 и серверные агрегаты на реальном доверенном XLSX с полным rollback; contract-тесты проверяют ответ bounded-read. Ручная UI-приёмка остаётся до завершения этапа.
- **Откат:** переключатель чтения пилота возвращает страницу на локальный V4-репозиторий; серверная партия остаётся для аудита.

### 5. Изолированные аналитические сценарии

- **Предварительный порядок:** Конкуренты → География → CX hardening → Точки входа → Поисковые запросы → Воронка/реклама.
- **Результат:** каждый сценарий переносится законченным вертикальным срезом и принимается отдельно.
- **Зависимости:** справочник обязателен для товарных источников; поиск зависит от «Рынка» и «Точек входа»; CX переиспользует общую инфраструктуру партий, но сохраняет версии методологии.
- **Проверка:** профильные формулы и фильтры, контрольные данные, pagination/aggregate contract, повторный импорт и rollback партии.
- **Откат:** feature flag чтения на уровне сценария; V4 остаётся рабочим источником до приёмки.

### 6. Критические бизнес-сценарии

- **Предварительный порядок:** Рентабельность → Планирование → Главная/карточка товара → Отчётность.
- **Результат:** финансовые источники, планы и объединяющие страницы работают на едином серверном наборе.
- **Зависимости:** все общие справочники, ежедневные факты, права и версионированные формулы.
- **Проверка:** денежные сверки по кабинетам/категориям/товарам, последовательное редактирование планов, согласованность Dashboard и отчётности, нагрузочные диапазоны.
- **Откат:** сценарный feature flag и read-only V4; никакой обратной записи V5 в IndexedDB V4.

### 7. Надёжность и командный доступ

- **Результат:** backup policy, проверенное восстановление, мониторинг партий/RPC, инструкции оператора и базовые роли коллег.
- **Зависимости:** стабильные схемы и реальные объёмы.
- **Проверка:** восстановление последней копии в отдельную среду; коллега по инструкции загружает файл, проверяет партию и открывает результат без помощи разработчика.
- **Откат:** восстановление в новый проект и смена только V5 environment configuration.
- **Текущий статус:** состав пакета, безопасные команды и prerequisite-check описаны в [V5_BACKUP_RECOVERY](V5_BACKUP_RECOVERY.md). Это не закрывает этап: на машине нет инструмента дампа, Auth mapping и restore в отдельный проект ещё не проверены.

### 8. Release candidate и переключение

- **Результат:** составной Pages deployment сохраняет V4 и добавляет V5; после приёмки V5 становится основной.
- **Зависимости:** все обязательные release gates ниже.
- **Проверка:** smoke/regression, доступ, import, backup restore и контрольные сверки в release environment.
- **Откат:** вернуть routing на неизменённую V4, остановить V5-import endpoints и сохранить V5 БД/логи для расследования.

## Обязательные условия релиза V5

- согласованный список ежедневных сценариев полностью перенесён и принят владельцем;
- по каждому сценарию сохранён путь `источник → партия → нормализованные строки → версия расчёта → UI`;
- контрольные суммы/строки/агрегаты V4 и V5 сверены, все различия объяснены;
- повторная и частичная загрузка не создаёт дублей и не затирает поля другого источника;
- неуспешная партия атомарно исключена из рабочих данных и может быть диагностирована;
- viewer/importer/admin и кабинетные ограничения проверены реальными пользователями;
- исходные файлы, история партий и версии методологии доступны для аудита;
- резервная копия создана и фактически восстановлена в отдельной среде;
- серверные выборки агрегированы/пагинированы и проверены на реальном объёме;
- документация и встроенная справка соответствуют реализации;
- коллега самостоятельно выполняет основной импорт и проверяет результат по инструкции;
- V4 сохранена как кодовый tag/branch и как отдельная резервная копия данных; её архивирование отдельно принимает владелец.

## Можно отложить после релиза

- автоматический импорт через WB/XWay API и расписания;
- новый редизайн и новые аналитические функции;
- расширенные роли сверх viewer/importer/admin;
- автоматические рекомендации и исправление методологических ошибок, выявленных при переносе;
- оптимизации, не требуемые измеренным объёмом/SLO;
- удаление V4 и её данных.

## Порядок переключения и отката

1. Зафиксировать commit/tag V4 и выполнить финальный экспорт её локальных данных.
2. Остановить изменения справочников и ручные импорты V4 на короткое согласованное окно.
3. Загрузить финальный delta в V5 и выполнить автоматические и ручные сверки.
4. Создать pre-release backup V5 и доказать восстановление в отдельный проект.
5. Опубликовать составной Pages artifact: неизменённая V4 остаётся доступной, V5 появляется по `/Analytics/v5/`.
6. Провести пользовательскую приёмку; только после неё переключить основную навигацию/URL на V5.
7. При инциденте вернуть вход на V4, сделать V5 read-only, остановить импорт и исследовать партию по журналу. При повреждении восстановить V5 в новый проект из проверенной копии.
8. Архивировать V4 только по отдельному подтверждению владельца; код, исходные файлы и backup остаются доступными для восстановления.

## НУЖНО СДЕЛАТЬ ВАМ

Foundation и backend-пилот «Рынок» применены и повторяемо проверяются командами `npm run db:v5:smoke`, `npm run db:v5:smoke-roles`, `npm run db:v5:smoke-market` и `npm run db:v5:smoke-market-file -- <путь-к-доверенному-xlsx>`. Первый admin создан; отдельные viewer/importer потребуются только перед релизом. Пароли и токены в чат не передаются.

До контрольного переноса данных в рабочей V4 нужно скачать «Разработка → Данные → Резервная копия V4» и сохранить JSON вместе с исходными отчётами вне репозитория.

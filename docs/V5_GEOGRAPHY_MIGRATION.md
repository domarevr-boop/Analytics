# Перенос «Географии» V4 → V5

Проверено: **10 сентября 2026**. Этап: аудит, версионное хранение, server import, bounded read API и выключенный frontend-адаптер завершены; parser/Web Worker и gated Import UI реализованы, но внешний smoke реального файла ещё не разрешён владельцем.

## Контрольный срез

Команда `npm run backup:v4:inspect-geography -- "<путь-к-backup.json>"` потоково извлекает только массив `geography` и справочник товаров, а затем выводит агрегированные счётчики без строк отчёта.

Для backup `analytics-v4-backup-2026-09-06.json` подтверждено:

- 189 431 исходная строка за 15 июня — 31 августа 2026 года, 78 календарных дней;
- 768 товаров, 13 кластеров, 148 областей и 9 176 населённых пунктов;
- 0 пропущенных/неизвестных товаров, регионов и некорректных дат;
- 0 отрицательных, дробных или нечисловых значений заказов и 0 отрицательных значений СВД;
- 23 055 повторов после нормализации пробелов и пустых уровней, но 0 конфликтующих payload; V4-семантика «последняя строка побеждает» даёт 166 376 канонических строк;
- канонический баланс: 219 024 заказа = 187 962 FBO + 31 062 FBS, остаток 0; разбиение локальных/нелокальных заказов товара также полностью сходится;
- СВД отсутствует у 132 234 канонических строк, покрывающих 111 518 заказов; такие строки входят в объём, но исключаются из среднего СВД;
- агрегатных строк без области/города, которые пришлось бы подавлять при наличии детализации, в контрольном срезе нет.

Сырые суммы до дедупликации не являются контрольным результатом: повторяющиеся нормализованные ключи увеличивают их до 280 315 заказов. Для сверки V5 используется только канонический набор.

## Зафиксированный контракт

- Grain: `date + product_id + region + normalized_area + normalized_city`.
- Пустая область нормализуется в `Без региона`, пустой город — в `Без населённого пункта`; пробелы по краям не образуют новую территорию.
- При повторе ключа действует детерминированная V4-совместимая замена последней строкой исходного порядка. Сервер обязан журналировать число замен и отклонять противоречащие ограничениям значения до публикации.
- FBO = `wb_local_orders + wb_nonlocal_orders`; FBS = `marketplace_local_orders + marketplace_nonlocal_orders`; локальность остаётся полем расчёта, а не отдельным UI-фильтром.
- `orders_total` обязан совпадать с FBO + FBS и с `product_local_orders + product_nonlocal_orders`; нарушение блокирует публикацию партии.
- Неизвестный СВД хранится как `null`, не как ноль. Он не участвует во взвешенном среднем, а покрытие показывается отдельно.
- Денежные показатели FBO/FBS остаются пропорциональной атрибуцией от общей суммы/прибыли товара за дату: источник не содержит отдельных денежных полей по типу исполнения.
- Исходный файл должен храниться в private Storage, партия — проходить staging и серверную валидацию, а аналитике видна только целиком опубликованная версия.

## Реализованное серверное хранение

Миграции `20260910015000_v5_geography_storage.sql` и `20260910016000_v5_geography_cabinet_versions.sql` применены в dev V5. Они создают `analytics.geography_order_versions`, связывают batch и факты одним `cabinet_id`, задают составной ключ версии, ограничения обоих балансов заказов и nullable СВД. Прямое чтение таблицы закрыто; `v5_geography_snapshot_bounds()` возвращает только агрегированные границы, собранные из последней опубликованной партии каждого доступного пользователю кабинета.

Remote dry-run показал ровно одну ожидаемую миграцию. Транзакционный `geography_storage_smoke.sql` подтвердил нормализацию, замену снимка, возврат предыдущей версии после отмены и запрет несходящегося fulfillment; все fixtures откатились. `db lint --linked --level warning` не нашёл ошибок.

Миграция `20260910017000_v5_geography_import.sql` реализует `.xlsx`-партию на выбранный доступный кабинет, private Storage, повтор по SHA-256, очистку staging при retry, передачу чанками до 500 строк и максимум 250 000 строк в партии. Сервер сопоставляет `seller_sku`/`wb_sku` только со справочником выбранного кабинета, отклоняет отсутствующий или неоднозначный товар, даты, числа, отрицательный СВД и оба нарушения баланса. Повторы нормализованного ключа сворачиваются последней исходной строкой, а их число сохраняется в metadata.

Remote smoke подтвердил успешную публикацию, private-source gate, идемпотентность, кабинетное сопоставление, дедупликацию, изоляцию ошибочной партии и admin rollback; все fixtures и Storage-объекты откатились. Повторный `db lint` не нашёл ошибок.

Миграция `20260910018000_v5_geography_read_api.sql` добавляет текущие версии по каждому доступному кабинету и пять bounded RPC: каскадные географические фильтры, KPI All/FBO/FBS, дневные ряды, пагинированные агрегаты уровня регион/область/город и лидеров товаров. Диапазон ограничен 731 днём, список кабинетов — 100, товаров — 500, page size — 200, offset — 100 000. Remote smoke подтвердил формулы заказов, взвешенный СВД и покрытие, фильтры, динамику, локации и SKU; db lint чист.

Денежные показатели, чистая прибыль и рентабельность намеренно не добавлены в geography RPC: их серверные источники ещё не перенесены, а выдумывать самостоятельную сумму из количества заказов нельзя.

## Frontend import и read-адаптер

`src/features/geography/geographyImportCore.ts` распознаёт фактические заголовки WB, сохраняет реальные Excel-даты, переводит `Xд Yч` в часы, не превращает ошибочный непустой текст в ноль и до staging сворачивает нормализованные повторы правилом «последняя строка побеждает». `.xlsx` до 25 MiB разбирается отдельным Web Worker; staging использует чанки по 500 строк. Import UI требует явный кабинет из `v5_directory_filters`, показывает исходные/канонические строки и повторы, сохраняет source в private Storage и публикует через готовый серверный lifecycle. Путь включается только сочетанием `VITE_APP_ENV=v5-development` и `VITE_V5_GEOGRAPHY_IMPORT_ENABLED=true`.

Контрольный файл `Геоография заказов.xlsx` локально разобран тем же core: 1 059 строк, 257 уникальных пар seller SKU/WB SKU, одна дата 18 июля 2026 года, 2 957 заказов = 2 957 FBO + 0 FBS, ошибочных значений СВД нет. Подготовленный `npm run db:v5:smoke-geography-file -- "<файл.xlsx>"` создаёт временный кабинет/товары, сверяет публикацию, snapshot и All/FBO/FBS через реальные RPC и заканчивается `rollback`. Его запуск остановлен политикой среды до отдельного информированного разрешения на передачу нормализованного содержимого реального файла во внешний dev-проект Supabase; постоянных данных этим запуском не создано.

`geographyDataCore.ts` и `geographyData.ts` типизируют и проверяют все пять read RPC: период до 731 дня, до 100 кабинетов/500 товаров, каскадные фильтры, полную сводку All/FBO/FBS, дневной баланс, nullable СВД, location pagination и уникальные product leaders. `VITE_V5_GEOGRAPHY_BACKEND_ENABLED=false` остаётся выключенным в staging до постоянной загрузки справочника и browser-приёмки страницы.

## Следующие gates

1. Получить отдельное разрешение владельца и выполнить транзакционный внешний smoke контрольного `.xlsx`; затем принять preview/cancel/publish в браузере.
2. Переключить страницу на готовый типизированный read-адаптер только после постоянной сверенной загрузки справочника.
3. Принять импорт и страницу под admin/importer/viewer в браузере.

До выполнения этих gates V5-страница «География» остаётся на локальном V4-store и не считается серверным сценарием.

# Supabase V5

Этот каталог содержит только активный backend-контур V5. Исторические миграции и функция V4/CX сохранены в `legacy-v4/` и не участвуют в `supabase db push`.

Миграции `20260906000000`–`20260908012000` применены к `analytics-v5-dev`. Migration list совпал, `db lint --linked --level warning` не нашёл проблем, health RPC вернул `20260908012000`, а private bucket `v5-import-sources` существует. `npm run db:v5:smoke` подтверждает 13 источников, 24 V5-таблицы, RLS на всех 24 и отсутствие публичного bootstrap. Первый Auth-пользователь назначен администратором; admin/viewer/importer проверены транзакционно. Миграция `20260909013000_v5_competitors_read_api.sql` подготовлена локально и не входит в этот подтверждённый remote-диапазон: перед dry-run/push новой сессии требуется `supabase login`.

## Защита окружения

- Разрешена только ветка `v5/*` и worktree с именем `Analytics-v5`.
- Project ref зафиксирован в `scripts/assert-v5-environment.mjs` и сверяется с `.env.local` и `supabase/.temp/project-ref`.
- `.env.local`, CLI-link metadata и ключи не коммитятся.
- Удалённые миграции запускаются только через `npm run db:v5:push`, а не прямой `supabase db push`.
- Перед link/push необходимо отдельно убедиться, что проект V4 не выбран.

## Активные миграции

`migrations/20260906000000_v5_foundation.sql` создаёт:

- закрытые схемы `app`, `ingest`, `core`, `analytics`;
- роли приложения и кабинетные разрешения;
- реестр 12 источников;
- партии, исходные файлы, сырые строки, ошибки и события импорта;
- версионированный каталог методик;
- приватный bucket `v5-import-sources`;
- RLS и минимальные health/access RPC.

Миграция не переносит рабочие данные и не меняет формулы. Обработка и публикация конкретного источника добавляются отдельными миграциями после проверки этого фундамента.

`migrations/20260906001000_v5_access_management.sql` добавляет неизменяемый журнал доступа, закрытый bootstrap первого администратора и admin-only RPC для ролей и кабинетных разрешений. Саморегистрация первым администратором невозможна.

`migrations/20260907003000_v5_access_directory.sql` добавляет admin-only каталог Auth-пользователей для V5-админки. Email и роли не доступны viewer/importer; изменение доступа продолжает выполняться через журналируемый RPC `v5_admin_set_user_access`.

`migrations/20260906002000_v5_market_pilot.sql` добавляет backend-пилот «Рынок»: версионные дневные факты, создание партии, staging, серверную валидацию, атомарную публикацию/отмену и агрегированные RPC. `20260906003000` квалифицирует функцию хеширования и исправляет volatility даты; `20260906004000` вводит монотонный порядок версий; `20260906005000` добавляет ограниченную сводку партии для Import UI; `20260907000000`–`20260907002000` добавляют безопасную очистку незавершённого staging перед повторной передачей и согласованную метку `uploaded_at`. Последующие миграции не переписывают историю уже применённого SQL.

`migrations/20260907004000_v5_market_batch_history.sql` возвращает до 50 последних партий «Рынка» с периодом, счётчиками, ошибками, попытками и наличием исходника. Importer видит только разрешённые ему партии, admin — все; UI запрашивает последние 20.

`migrations/20260907005000_v5_market_batch_errors.sql` возвращает до 200 построчных ошибок одной доступной партии. UI загружает не более 100 записей по запросу пользователя; viewer и чужая партия отклоняются до чтения ошибок.

`migrations/20260907006000_v5_market_source_download.sql` добавляет к bounded-журналу object path сохранённого исходника. UI скачивает файл напрямую из private Storage только после серверной проверки видимости партии и повторной проверки Storage RLS; публичная ссылка не создаётся.

`migrations/20260907007000_v5_market_batch_events.sql` возвращает до 200 этапов одной доступной партии без раскрытия идентификатора исполнителя. UI по запросу показывает до 100 событий в хронологическом порядке.

`migrations/20260907008000_v5_product_directory.sql` добавляет пустой серверный справочник: бренды, категории, товары, кабинетные алиасы, склейки и датированную историю состава. Identity SKU/WB ID/алиаса ограничена кабинетом; resolver возвращает последнее известное состояние на дату и отличает неизвестное состояние от явной группы «Без склейки». Рабочие данные V4 миграция не переносит.

`migrations/20260908009000_v5_directory_bootstrap.sql` добавляет атомарную публикацию сохранённого bootstrap-манифеста, его lineage к backup V4, legacy mapping и очередь неоднозначных identity. Публикация требует private Storage-объект и полностью отменяется при конфликте.

`migrations/20260908010000_v5_directory_read_api.sql` добавляет bounded выдачу справочника (до 500 строк), поиск по основным identity и алиасам, разрешение склейки на дату и доступные пользователю фильтры. Каждый результат повторно ограничен кабинетным доступом на сервере.

`migrations/20260908011000_v5_competitors_storage.sql` добавляет четыре версионные таблицы конкурентного файла с независимой гранулярностью, RLS по доступу к партии и bounded RPC границ. Один последний опубликованный batch заменяет весь четырёхлистовой срез; отмена возвращает предыдущую версию. Серверный импорт и агрегаты страницы добавляются отдельно.

`migrations/20260908012000_v5_competitors_import.sql` добавляет создание партии, private Storage lineage, повтор по SHA-256 без дублей, очистку staging для retry, порционную загрузку и атомарную серверную валидацию/публикацию всех четырёх секций. Ограничения текущего ручного контура: XLS/XLSX до 25 MiB, 500 строк за вызов и 50 000 строк на партию.

## Применение

1. Выполнить `npx supabase login` локально; токен не добавлять в репозиторий.
2. В этом worktree выполнить `npx supabase link --project-ref <V5_PROJECT_REF>` и ввести пароль БД V5 локально.
3. Выполнить `npm run db:v5:guard`.
4. Просмотреть план изменений через `npm run db:v5:dry-run`.
5. Только после проверки выполнить `npm run db:v5:push`.
6. После применения выполнить read-only проверку `npm run db:v5:smoke`.
7. Для пилота «Рынок» выполнить `npm run db:v5:smoke-market`: тест публикует валидную и ошибочную партии, проверяет расчёты, замену и откат, затем отменяет всю транзакцию.
8. Для сверки реального доверенного отчёта выполнить `npm run db:v5:smoke-market-file -- "<полный путь>.xlsx"`: команда сверяет нормализованные строки parser V4/V5, серверные итоги и делает `ROLLBACK`; файл в Git не добавляется.
9. Проверить готовность recovery-инструментов командой `npm run db:v5:backup:check`. Она не создаёт backup; полная процедура и незакрытые ограничения находятся в `docs/V5_BACKUP_RECOVERY.md`.
10. Для пустого серверного справочника выполнить `npm run db:v5:smoke-directory`: кабинетные identity и переходы склеек проверяются с обязательным `ROLLBACK`.
11. До bootstrap справочника проверить внешний backup V4 командой `npm run backup:v4:inspect -- "<путь-к-backup.json>"`. Скрипт потоково возвращает только размеры и агрегированную диагностику, не импортирует и не печатает строки.
12. Контракт атомарной публикации справочника проверить `npm run db:v5:smoke-directory-bootstrap`, а bounded чтение и склейку на дату — `npm run db:v5:smoke-directory-read`; обе команды используют тестовые fixtures только внутри транзакции с `ROLLBACK`.
13. Контракт версионного хранилища «Конкурентов» проверить `npm run db:v5:smoke-competitors-storage`: команда создаёт две тестовые партии, проверяет полную замену и откат, затем отменяет транзакцию.
14. Полный lifecycle импорта «Конкурентов» проверить `npm run db:v5:smoke-competitors-import`: команда проверяет исходник, duplicate hash, retry-reset, четыре обязательные секции, ошибочную партию и rollback внутри одной отменяемой транзакции.
15. Bounded чтение «Конкурентов» проверить `npm run db:v5:smoke-competitors-read`: команда сверяет фильтры, дневные KPI, бренды, карточки, максимум частотности запроса, приоритет складских снимков и TOP-движение и всегда выполняет `ROLLBACK`.

## Первый администратор

1. В Supabase Dashboard проекта `analytics-v5-dev` создать ровно одного Auth-пользователя. Пароль остаётся у владельца и не передаётся агенту.
2. Убедиться через `npm run db:v5:smoke`, что `auth_user_count` равен `1`, а `assigned_role_count` равен `0`.
3. Явно запустить `npm run db:v5:bootstrap-admin`. Команда защищена V5 guard, откажется работать при нуле или нескольких Auth-пользователях и не принимает email/пароль.
4. Повторить smoke-test: ожидаются `auth_user_count: 1` и `assigned_role_count: 1`.
5. Выполнить `npm run db:v5:smoke-admin`: проверка запускается как `authenticated`, проверяет admin RPC и всегда откатывает тестовую транзакцию.

После bootstrap дальнейшие роли и кабинетные разрешения меняются только admin-only RPC и фиксируются в `app.access_audit`.

До появления отдельных тестовых аккаунтов команда `npm run db:v5:smoke-roles` проверяет viewer/importer, кабинетную изоляцию и разрешённое создание партии на существующем Auth-пользователе. Обе проверки выполняются в транзакциях с обязательным `ROLLBACK`, поэтому admin-роль, тестовые кабинеты и партия не сохраняются. Это не заменяет финальную проверку несколькими реальными пользователями перед релизом.

Локальные `supabase start` и `supabase db dump` пока недоступны, потому что Docker на машине не установлен. Не используйте `supabase db dump --dry-run` в общих логах: CLI может вывести временные реквизиты подключения.

# Supabase V5

Этот каталог содержит только активный backend-контур V5. Исторические миграции и функция V4/CX сохранены в `legacy-v4/` и не участвуют в `supabase db push`.

Foundation `20260906000000` и управление доступом `20260906001000` применены к `analytics-v5-dev` 6 сентября 2026. После применения migration list совпал, `db lint --linked` не нашёл ошибок, health RPC вернул ожидаемую версию, anon REST не увидел приватную ingest-таблицу, а private bucket `v5-import-sources` существует и пуст. `npm run db:v5:smoke` дополнительно подтвердил 12 источников, 11 V5-таблиц, RLS на всех 11 и отсутствие публичного доступа к bootstrap-функции. Первый Auth-пользователь назначен администратором; `npm run db:v5:smoke-admin` подтвердил его права и откатил тестовую транзакцию.

## Защита окружения

- Разрешена только ветка `v5/*` и worktree с именем `Analytics-v5`.
- Project ref зафиксирован в `scripts/assert-v5-environment.mjs` и сверяется с `.env.local` и `supabase/.temp/project-ref`.
- `.env.local`, CLI-link metadata и ключи не коммитятся.
- Удалённые миграции запускаются только через `npm run db:v5:push`, а не прямой `supabase db push`.
- Перед link/push необходимо отдельно убедиться, что проект V4 не выбран.

## Активная миграция

`migrations/20260906000000_v5_foundation.sql` создаёт:

- закрытые схемы `app`, `ingest`, `core`, `analytics`;
- роли приложения и кабинетные разрешения;
- реестр 12 источников;
- партии, исходные файлы, сырые строки, ошибки и события импорта;
- версионированный каталог методик;
- приватный bucket `v5-import-sources`;
- RLS и минимальные health/access RPC.

Миграция не переносит рабочие данные и не меняет формулы. Обработка и публикация конкретного источника добавляются отдельными миграциями после проверки этого фундамента.

`migrations/20260906001000_v5_access_management.sql` добавляет неизменяемый журнал доступа, закрытый bootstrap первого администратора и admin-only RPC для ролей и кабинетных разрешений. Саморегистрация первым администратором невозможна.

## Применение

1. Выполнить `npx supabase login` локально; токен не добавлять в репозиторий.
2. В этом worktree выполнить `npx supabase link --project-ref <V5_PROJECT_REF>` и ввести пароль БД V5 локально.
3. Выполнить `npm run db:v5:guard`.
4. Просмотреть план изменений через `npm run db:v5:dry-run`.
5. Только после проверки выполнить `npm run db:v5:push`.
6. После применения выполнить read-only проверку `npm run db:v5:smoke`.

## Первый администратор

1. В Supabase Dashboard проекта `analytics-v5-dev` создать ровно одного Auth-пользователя. Пароль остаётся у владельца и не передаётся агенту.
2. Убедиться через `npm run db:v5:smoke`, что `auth_user_count` равен `1`, а `assigned_role_count` равен `0`.
3. Явно запустить `npm run db:v5:bootstrap-admin`. Команда защищена V5 guard, откажется работать при нуле или нескольких Auth-пользователях и не принимает email/пароль.
4. Повторить smoke-test: ожидаются `auth_user_count: 1` и `assigned_role_count: 1`.
5. Выполнить `npm run db:v5:smoke-admin`: проверка запускается как `authenticated`, проверяет admin RPC и всегда откатывает тестовую транзакцию.

После bootstrap дальнейшие роли и кабинетные разрешения меняются только admin-only RPC и фиксируются в `app.access_audit`.

Локальный `supabase start` пока недоступен, потому что Docker на машине не установлен.
